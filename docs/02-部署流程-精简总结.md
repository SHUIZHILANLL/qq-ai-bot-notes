# QQ 机器人部署 · 精简总结

> 这是压缩版：**「照着能重做一遍」**。讲原理的完整版看 [QQ机器人部署教程.md](QQ机器人部署教程.md)。
> 场景：阿里云 ECS（Ubuntu 24.04）+ SnowLuma + DSH + qq-bridge，QQ 机器人接大模型。

---

## 一、一句话架构

```
QQ服务器 ⇄ SnowLuma(容器) ⇄ qq-bridge(Node) ⇄ DSH(AI)
          把QQ变成API      翻译+记忆+唤醒        agent本体
```

**必须同机**：桥接要用 `~/.dsh` 的本地凭证离线签发 cookie 去连 DSH，所以三者不能拆开。
**必须隔离**：SnowLuma 的四个端口（3000/3001/5099/6081）合起来等于 QQ 的完全控制权，
全部绑 `127.0.0.1` + 安全组只开 22，靠 SSH 隧道访问。

## 二、部署流程（12 步）

### 准备

```bash
# 1. 建普通用户（别一直用 root）
useradd -m -s /bin/bash --disabled-password qqbot
echo 'qqbot ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/qqbot
cp -r /root/.ssh /home/qqbot/ && chown -R qqbot:qqbot /home/qqbot/.ssh

# 2. 装 Docker（用发行版源，比 docker-ce 官方源快一个数量级）
sudo apt-get install -y docker.io docker-compose-v2
sudo usermod -aG docker qqbot

# 3. ⚠️ 配镜像加速器 —— 阿里云 ECS 上 Docker Hub 完全不通，不配后面必挂
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://dockerproxy.net",
    "https://docker.1panel.live"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
EOF
sudo systemctl restart docker
sudo docker pull alpine    # ← 必须实测，别只看配置文件

# 4. 装 Node + pnpm
cd /tmp
curl -fsSLO https://npmmirror.com/mirrors/node/v24.9.0/node-v24.9.0-linux-x64.tar.xz
sudo tar -xJf node-v24.9.0-linux-x64.tar.xz -C /usr/local --strip-components=1
npm config set registry https://registry.npmmirror.com
sudo npm i -g @deepseek-ai/dsh pnpm      # ⚠️ pnpm 必须装，Linux 上 DSH 不自带
```

### 三个组件

```bash
# 5. SnowLuma 容器（compose 关键项）
#    cap_add: SYS_PTRACE        ← 注入 QQ 必需
#    security_opt: seccomp=unconfined
#    shm_size: 1gb              ← Chromium 需要，默认 64MB 会崩
#    ports 全部 "127.0.0.1:xxx:xxx"
sudo docker compose up -d
sudo docker exec snowluma getcap /usr/local/bin/node   # 要看到 cap_sys_ptrace=ep

# 6. DSH 凭证搬过来 + 收权限
scp ~/.dsh/.credentials.yaml qqbot@IP:/home/qqbot/.dsh/
chmod 600 ~/.dsh/.credentials.yaml        # ⚠️ 不是 600 的话 DSH 拒绝启动

# 7. dsh 服务（端口必须钉死，桌面版默认随机端口）
#    ExecStart=/usr/bin/env dsh web --host 127.0.0.1 --port 3080 --no-open
sudo systemctl enable --now dsh

# 8. 桥接
git clone https://github.com/Derpyu520/qq-bridge.git ~/qq-bridge
cd ~/qq-bridge && npm install
# config.json: dsh.baseUrl 对齐 3080 / snowluma.homeDir 指向容器数据目录 / allow 白名单
node scripts/setup-dsh.mjs
node scripts/verify-agent-presets-017.mjs http://127.0.0.1:3080   # 独立验证

# 9. 服务单元（⚠️ 用 /usr/bin/env，别写死 /usr/bin/node）
#    ExecStart=/usr/bin/env node src/bridge.js
sudo systemctl enable --now qq-bridge
```

### 上线

```bash
# 10. 扫码登录 QQ（唯一需要人工的一步）
#     本地开隧道，浏览器开 noVNC，手机 QQ 扫码
ssh -N -i ~/.ssh/key -L 6081:127.0.0.1:6081 qqbot@IP
#     判定成功的唯一标准（不是"端口在监听"）：
sudo docker logs snowluma 2>&1 | grep 'login detected'
ls aiqq/deploy/snowluma/data/config/onebot_*.json      # 出现这个文件才算真的上来了

# 11. 数据搬迁（"程序上云，灵魂也得搬"）
#     搬：.credentials.yaml / meme-packs / roles/*.md / config.json / state/*
#     不搬：sessions/（路径相关）、cache、attachments、node_modules
#     ⚠️ 最容易漏：人格的"当前启用哪个"在 state/current-role.json，
#        只传 roles/*.md 的话服务端 role=null，AI 会按默认 coding agent 说话

# 12. 确认三项自启
systemctl is-enabled dsh qq-bridge docker
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' snowluma   # unless-stopped
```

## 三、必踩的坑（速查）

| 现象 | 根因 | 修 |
|---|---|---|
| `docker pull` 超时 | ECS 上 Docker Hub 不通 | 配 registry-mirrors |
| 装 docker-ce 只有 40KB/s | "官方源"不是最快源 | 用发行版归档源 |
| `dsh` 崩溃循环 1/FAILURE | 凭证被 scp 传成 664 | `chmod 600` |
| `dsh plugin` 返回 127 | Linux 上 DSH 不带 pnpm | `npm i -g pnpm` |
| 桥接 `status=203/EXEC` | unit 写死 `/usr/bin/node` | 用 `/usr/bin/env node` |
| 整机假死、SSH 收不到 banner | 阿里云镜像把 `swappiness` 写死 0 → direct reclaim | 用 `99-zz-` 前缀覆盖 + zram |
| WS 反复 `unauthorized` | OneBot 的 HTTP 和 WS 是**两个不同 token** | 连之前先做 token 发现 |
| 看着"掉登录" | `SNOWLUMA_LOG_LEVEL=warn` 把 `login detected` 吞了 | 诊断时保持 `info` |
| QQ 崩溃后不自动登录 | 账号在别的电脑登录，把容器会话顶掉了 | 重新扫码；别在电脑登这个号 |
| 机器人哑了但服务全 active | 桥接的「会话繁忙」是**内存状态**，重启 dsh 没用 | 控制台 `/api/socialV2/wake` → 不行再 `/api/session/reset` |

**一条元规律**：上面 10 个坑里 6 个是「我以为 A，实际是 B」。
**所以每步都要配一个独立验证** —— 配了加速器就真拉个镜像，改了 swappiness 就真 `cat` 一下。

## 四、日常运维（只有三条）

```bash
# ① 体检（怀疑有问题就跑它，分层定位断在哪一层）
bash /home/qqbot/healthcheck.sh

# ② 解卡（机器人沉默十几分钟以上）
bash /home/qqbot/unstick.sh        # 先试无代价的唤醒接口，不行才提示重置

# ③ 重启（不动容器 → QQ 登录态保住）
sudo systemctl restart dsh qq-bridge
```

**三个访问入口**（都要先开隧道）：

```powershell
ssh -N -i <密钥> -L 3100:127.0.0.1:3100 -L 5099:127.0.0.1:5099 -L 6081:127.0.0.1:6081 qqbot@<IP>
```

| 入口 | 地址 | 用途 |
|---|---|---|
| 桥接控制台 | `127.0.0.1:3100` | 人格、模式、白名单、token 记账 |
| SnowLuma | `127.0.0.1:5099` | OneBot 配置、账号状态 |
| noVNC | `127.0.0.1:6081/vnc.html` | 重新扫码 |

## 五、出问题怎么查（分层，别乱猜）

```
QQ ──①── SnowLuma ──②── 桥接 ──③── DSH
```

| 层 | 怎么测 | 健康表现 |
|---|---|---|
| ① QQ 登录 | `docker logs snowluma \| grep 'login detected'` | 最近有记录 |
| ② OneBot | `curl -X POST localhost:3000/get_login_info` | `{"status":"ok"}` |
| ② 桥接收 QQ | `journalctl -u qq-bridge` | `SnowLuma 已连接` |
| ③ DSH | `/api/status` 的 `dshReady` | `true` |
| ③ AI 出话 | `/api/status` 的 `activity` | 有 `工具统一发送：成功 N/N 条` |

**心法：不要看「服务还活着吗」，要看「数据流到哪一步断的」。**
服务全是 `active` 却在装死，是这类系统最常见的故障形态。

## 六、三条硬教训

**① 资源要实测，不要估。** 这套东西实测吃 ~1.35GB（容器 750MB 里 QQ 的 Chromium 占 625MB）。
**2G 是极限，建议 4G。** 我当初按"2G 够用"推荐，结果聊 5 小时把机器顶穿、整机假死。

**② 写自动运维脚本前，先问"正常情况会不会也长这样"。**
我加过两个看门狗，**两个都造成了故障**：
- 卡死检测的判定条件（唤醒被暂存 + 无发送）和 AI 的"睡前观察"长等待完全重合 → 每 10 分钟误判、打断正常对话
- dsh 内存 GC 阈值定成 400MB，而 dsh 正常水位就是 400~460MB → 每十几分钟在回合中重启一次，把桥接留在「繁忙」状态

**监控的误报比不监控更糟 —— 它会主动破坏正常流程。**

**③ 任何"重置"类操作前先备份。**
`/api/session/reset` 会连 100 条聊天记录一起删，删完 AI 以为"这段私聊没历史"，反而更哑。
这次靠备份把记忆合并回去了。

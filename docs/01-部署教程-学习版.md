# QQ 机器人部署全流程 · 学习版

> 基于 2026-09-29 ~ 09-30 的一次真实部署复盘（阿里云 ECS 2核2G / Ubuntu 24.04）。
> **重点不是命令，是每一步"为什么"** —— 命令可以抄，判断力抄不来。
> 所有命令都是当时真实跑过的，遇到坑的地方都标了根因。

## 第 0 章 先搞懂架构（跳过这章，后面全是瞎抄）

### 0.1 四个角色的分工

```
        ┌──────────────────────────────────────────┐
        │            QQ 服务器（腾讯）              │
        └───────▲──────────────────────┬───────────┘
                │ ① 登录 + QQ 协议      │ ⑤ 收发消息
                │                       ▼
┌───────────────┴───────────────────────────────────────────┐
│  SnowLuma（Docker 容器）                                   │
│  职责：把「QQ 客户端」变成「HTTP / WebSocket 接口」        │
│   · 里面跑一个真实的 Linux QQ（Chromium 应用）             │
│   · 用 hook 注入的方式把 QQ 能力暴露成 OneBot v11 协议     │
│   · 端口：3000 HTTP / 3001 WS / 5099 WebUI / 6081 noVNC    │
└───────────────▲───────────────────────────────────────────┘
                │ ② OneBot 协议（HTTP + WS，带 accessToken）
                ▼
┌───────────────────────────────────────────────────────────┐
│  qq-bridge（Node 进程）                                    │
│  职责：「翻译官」+「AI 的嘴和耳朵」                        │
│   · 收 QQ 消息 → 判断要不要叫醒 AI → 组装提示词喂给 AI     │
│   · 收 AI 的工具调用 → 转成 OneBot 请求发消息/表情/拍一拍  │
│   · 维护：会话映射、记忆、唤醒策略、白名单、token 记账     │
│   · 自带控制台：3100                                       │
└───────────────▲───────────────────────────────────────────┘
                │ ③ DSH 的本地 HTTP API（3080）
                ▼
┌───────────────────────────────────────────────────────────┐
│  DSH（dsh web）                                           │
│  职责：AI 本体                                             │
│   · 跑 agent 循环：读提示词 → 请求大模型 → 调工具 → 循环  │
│   · 会话、上下文、工具调用都在这层                         │
│   · 它完全不知道 QQ 的存在，只知道"有人给我发了段话"       │
└───────────────────────────────────────────────────────────┘
```

**数据流一句话**：QQ 消息 → SnowLuma 转成 OneBot 事件 → 桥接判断要不要唤醒 →
组装提示词调 DSH → AI 思考并调用工具 → 桥接把工具调用转成 OneBot 请求 → QQ 发出消息。

### 0.2 三个必须理解的设计约束

**① 为什么要有桥接这一层？**
DSH 是通用 agent 框架，它不认识 QQ。桥接干两件事：
把 QQ 消息「翻译」成提示词、把 AI 的工具调用「翻译」回 QQ 操作。
没有它，AI 就只是个会聊天的文本框。

**② 为什么 SnowLuma 必须跑容器？**
它要在 Linux 上跑真实 QQ 客户端，还要 `ptrace` 注入到 QQ 进程里改行为。
容器把这些又脏又依赖系统的活封装好了（官方镜像已配好 `cap_sys_ptrace`、Xvfb、VNC）。

**③ 为什么这三样必须同机？**（这是选型时最容易忽略的）
桥接要用 `~/.dsh` 里的本地凭证**离线签发 cookie** 去连 DSH 的 API。
凭证在本地文件里 → 桥接和 DSH 必须能读到同一个 `~/.dsh` → **必须同机**。
这一条直接决定了架构：不能把 DSH 放 A 机器、桥接放 B 机器。

### 0.3 部署前的关键决策：本地还是云？

| | 本地（Windows） | 云（Linux 服务器） |
| --- | --- | --- |
| 优点 | 免费、QQ 客户端就是你自己在用的 | 7×24 在线，关电脑也能跑 |
| 缺点 | 关机就没了、DSH 端口随机变 | 要花钱、要处理 Linux 一堆坑 |
| 适合 | 先跑通验证 | 长期挂着 |

**学习建议：先在本地跑通，再迁云。** 本地出问题你能直接看到 QQ 窗口，云上只能靠日志。
本文按云端讲，但每步都标了「本地对应怎么做」。

## 第 1 章 云端准备

### 1.1 选机器

**要多少资源？** 实测这套东西的真实占用（这台 2核2G 机器上）：

| 组件 | 内存 |
| --- | --- |
| SnowLuma 容器（其中 QQ 的 Chromium 多进程约 625MB） | **~750 MB** |
| dsh | ~270–460 MB（随对话时长增长） |
| qq-bridge | ~80 MB |
| Docker + containerd | ~100 MB |
| 系统 + journald | ~120 MB |
| **合计** | **~1.35 GB** |

**结论：2G 是能跑的极限，但很紧。** 我当时按"2G 够用"推荐，结果聊了 5 小时把机器顶穿、
整机假死。**现在会建议至少 4G**，或者 2G + 做好调优（见第 4 章）。

**选规格的坑**：阿里云「99 计划」页面标的低价机型可能根本不是你要的配置。
我当时给了一个过时价格（u1 2核4G 199元/年），实际那档只有「经济型 e 2核2G 99元/年」。
**教训：价格和规格必须在控制台下单页现场确认，别信文章。**

### 1.2 SSH 密钥（比密码好得多）

本地生成密钥对：

```powershell
ssh-keygen -t ed25519 -f C:\Users\UFO\.ssh\aiqq_ed25519 -N "" -C "aiqq-aliyun"
```

- `-t ed25519`：现代算法，比 RSA 短且快
- `-N ""`：空密码（脚本用，不想要交互）
- **`.pub` 是公钥，要传到阿里云；没有后缀的那个是私钥，绝不能外传**

在阿里云控制台「密钥对」里导入公钥 → 绑定到实例 → **重启实例才生效**（我第一次没重启，连不上）。

### 1.3 首次登录常见坑

```powershell
ssh -i C:\Users\UFO\.ssh\aiqq_ed25519 root@<公网IP>
```

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Permission denied (publickey)` | 密钥没绑定 / 没重启生效 | 控制台确认绑定 + 重启实例 |
| `Connection refused` | 刚重启，sshd 还没起来 | 等 30 秒重试（**这是瞬时的，不是坏了**） |
| 一直超时 | 安全组没放行 22 端口 | 控制台 → 安全组 → 入方向加 22 |

> ⚠️ **工作流上的一个重要教训**：我一路给的是「在服务器里敲这条命令」，
> 而用户反复把 Windows 的 `PS C:\Users\UFO>` 和服务器里的 `qqbot@iZxxx:~$` 搞混，
> 甚至在自己电脑上敲 `sudo apt-get`（Windows 没 sudo）。
>
> **正确做法**：始终给「从本地发起」的一行命令，让用户只在一个地方粘贴：
> ```powershell
> ssh -i C:\Users\UFO\.ssh\aiqq_ed25519 qqbot@<IP> "要执行的命令"
> ```

### 1.4 建一个普通用户（别一直用 root）

```bash
# 建用户、给 sudo、把 root 的 authorized_keys 复制过去
useradd -m -s /bin/bash --disabled-password qqbot
usermod -aG sudo qqbot
echo 'qqbot ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/qqbot
mkdir -p /home/qqbot/.ssh
cp /root/.ssh/authorized_keys /home/qqbot/.ssh/
chown -R qqbot:qqbot /home/qqbot
chmod 700 /home/qqbot/.ssh && chmod 600 /home/qqbot/.ssh/authorized_keys
```

**为什么值得多这一步**：后面所有服务都以 `qqbot` 身份跑，
`~/.dsh`、`qq-bridge/state` 的权限才不会打架。

> 踩坑：`scp` **不会自动建目标目录**。我 `scp ... qqbot@IP:/home/qqbot/aiQQ/` 时报
> `realpath ... No such file`，而且 `mkdir -p /home/qqbot` 建出来的是 **root 属主**的目录，
> 导致 qqbot 写不进去。**先 `ssh` 进去用 qqbot 身份建目录，再 scp。**

### 1.5 装 Docker（有坑，但坑不在 Docker）

**第一步就要面对的现实：阿里云 ECS 上 Docker Hub 完全不通。**

```bash
curl -s -o /dev/null -w '%{http_code}' --max-time 10 https://registry-1.docker.io/v2/
# → 000（超时）
docker pull alpine
# → dial tcp 162.125.2.6:443: i/o timeout
```

**所以必须先配镜像加速器**（很多公共镜像 2024 年已关闭，得实测哪些还活着）：

```bash
# 实测各加速器可达性（401/200 都算通，401 是注册表的正常响应）
for m in docker.m.daocloud.io docker.1ms.run dockerproxy.net docker.1panel.live \
         docker.nju.edu.cn docker.mirrors.sjtug.sjtu.edu.cn mirror.ccs.tencentyun.com; do
  printf '%-40s ' "$m"
  curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' --max-time 8 "https://$m/v2/"
done
```

当时的结果：`daocloud` / `1ms.run` / `dockerproxy.net` / `1panel.live` 通，
`nju` 403、`sjtug` 不通、`mirror.ccs.tencentyun.com` 不通（那是腾讯云专用的）。

写进 `/etc/docker/daemon.json`：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://dockerproxy.net",
    "https://docker.1panel.live"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

> `log-opts` 这两行也重要：Docker 默认日志**无上限**，而 QQ 在无头环境会疯狂刷
> `DroppedFrame`，日志能一直涨到撑爆磁盘。

**第二个坑：Docker 官方源极慢。** 装 docker-ce 二十多分钟只下了 50MB（≈40 KB/s），
而实测 Ubuntu 归档源 **60 MB/s**（88MB 一秒下完）。**换成 Ubuntu 自带的就行**：

```bash
sudo apt-get install -y docker.io docker-compose-v2
# Ubuntu 24.04 里就是 Docker 29.1.3 + Compose 2.40.3，功能完全够
sudo usermod -aG docker qqbot
```

> 教训：**"官方源"不等于"最快的源"**。在国内云主机上，发行版归档源往往快一个数量级。
> 怀疑网络慢时，先做一次速度实测再决定换不换源。

### 1.6 装 Node + pnpm

```bash
# 用 npmmirror 的二进制包（比 NodeSource 源快很多）
cd /tmp
curl -fsSLO https://npmmirror.com/mirrors/node/v24.9.0/node-v24.9.0-linux-x64.tar.xz
sudo tar -xJf node-v24.9.0-linux-x64.tar.xz -C /usr/local --strip-components=1
node -v && npm -v

npm config set registry https://registry.npmmirror.com
sudo npm i -g @deepseek-ai/dsh
sudo npm i -g pnpm      # ← 必须！见下面的坑
```

> ⚠️ **坑：Linux 上 DSH 不自带 pnpm。** Windows 桌面版自带，Linux 用 npm 全局装就没有。
> 后果是 `dsh plugin --profile web add/install` 报 `pnpm was not found`，
> **退出码 127**，表现是插件装不上、profile bundle 解析失败。这个错误信息很有迷惑性
> （127 一般被当成"命令找不到"，但其实 `dsh` 本身在，是它内部的 pnpm 找不到）。

## 第 2 章 三个组件逐个部署

### 2.1 目录规划

```
/home/qqbot/
├── aiQQ/deploy/              ← 部署包（compose 文件、脚本、挂载点）
│   ├── docker-compose.yml
│   ├── .env
│   ├── setup.sh
│   ├── snowluma/             ← 容器数据（bind mount，持久化）
│   │   ├── data/    → /app/data
│   │   ├── config/  → /app/.config
│   │   └── local/   → /app/.local/share
│   └── systemd/              ← 服务单元模板
├── qq-bridge/                ← 桥接源码
│   ├── src/bridge.js
│   ├── config.json
│   ├── roles/                ← 人格卡
│   └── state/                ← 会话映射、记忆、token
└── .dsh/                     ← DSH 的家
    ├── .credentials.yaml     ← API 凭证（mode 必须 600！）
    ├── sessions/             ← 会话事件日志
    └── profiles/web/         ← profile（插件、preset）
```

**为什么用 bind mount 而不是 docker volume**：出问题时能直接 `ls` 看文件、
能备份、能 `scp` 出来。学习和排错阶段，可见性比"优雅"重要得多。

### 2.2 SnowLuma（QQ 侧）

`docker-compose.yml` 的关键部分：

```yaml
services:
  snowluma:
    image: motricseven7/snowluma:latest
    container_name: snowluma
    restart: unless-stopped
    cap_add:
      - SYS_PTRACE                    # ← 注入 QQ 进程必需，缺了 hook 起不来
    security_opt:
      - seccomp=unconfined            # ← ptrace 会被默认 seccomp 拦掉
    shm_size: 1gb                     # ← Chromium 需要大 /dev/shm，默认 64MB 会崩
    ports:
      - "127.0.0.1:3000:3000"         # OneBot HTTP
      - "127.0.0.1:3001:3001"         # OneBot WS
      - "127.0.0.1:5099:5099"         # WebUI
      - "127.0.0.1:6081:6081"         # noVNC（扫码用）
    env_file: .env
    volumes:
      - ./snowluma/data:/app/data
      - ./snowluma/config:/app/.config
      - ./snowluma/local:/app/.local/share
```

**「全部绑 127.0.0.1」是这套部署最重要的安全决策。**
这四个端口合起来等于你 QQ 的完全控制权。绑在 127.0.0.1 + 安全组只开 22，
意味着**从公网根本访问不到**，只能通过 SSH 隧道进来。

`.env` 里两个要紧的：

```bash
SNOWLUMA_SCREEN=1280x720x16   # 虚拟屏幕；省内存可以降到 800x600x16
SNOWLUMA_LOG_LEVEL=info       # ⚠️ 别随便调成 warn，见下面第 4 章的坑
```

**拉镜像**（前面配了加速器，实测 2.7GB 的镜像能正常拉下来）：

```bash
sudo docker compose up -d
```

**验证清单**（缺一项后面都会出问题）：

```bash
sudo docker ps                                    # Up
sudo docker exec snowluma getcap /usr/local/bin/node
#   → cap_sys_ptrace=ep        ← 没有这个，注入会失败
sudo docker exec snowluma supervisorctl status
#   → qq RUNNING / snowluma RUNNING
ss -tlnp | grep -E ':(3000|3001|5099|6081)'      # 都应是 127.0.0.1
```

**扫码登录 QQ**（这一步没法自动化，必须人工）：

```powershell
# 本地开隧道（-N 表示只转发不执行命令；窗口会"卡住"，这是正常的）
ssh -N -i C:\Users\UFO\.ssh\aiqq_ed25519 `
    -L 6081:127.0.0.1:6081 -L 5099:127.0.0.1:5099 qqbot@<IP>
```

浏览器打开 `http://127.0.0.1:6081/vnc.html` → 输 VNC 密码 → 手机 QQ 扫码。

**登录成功的判定**（不要只看端口在监听）：

```bash
sudo docker logs snowluma 2>&1 | grep 'login detected'
# → OK [Hook] login detected: PID=79 UIN=<QQ号>
ls aiQQ/deploy/snowluma/data/config/onebot_*.json
# → 出现 onebot_<QQ号>.json 才说明账号真的上来了
```

### 2.3 DSH（AI 侧）

先**把凭证搬过来**，这是最容易漏的一步：

```powershell
scp -i C:\Users\UFO\.ssh\aiqq_ed25519 "$env:USERPROFILE\.dsh\.credentials.yaml" qqbot@<IP>:/home/qqbot/.dsh/
ssh -i C:\Users\UFO\.ssh\aiqq_ed25519 qqbot@<IP> "chmod 600 ~/.dsh/.credentials.yaml"
```

> ⚠️ **坑：权限必须是 600。** DSH 有安全护栏，读到 mode 664 会**直接拒绝启动**：
> ```
> Error: credentials-local: ~/.dsh/.credentials.yaml is readable beyond its owner (mode 664)
> ```
> 而 `scp` 传过来的文件默认就是 664（Windows 的权限映射过来很奇怪）。
> 症状是 `dsh.service` 崩溃循环、`status=1/FAILURE`，光看 journal 前几行看不出所以然。

**为什么 DSH 要用 systemd 管理、并钉死端口？**

DSH 桌面版用 `dsh web --port 0`（**随机端口**），桥接的 `dsh.baseUrl` 是启动时读进内存的 ——
DSH 一重启桥接就连不上。本地反复踩过（端口从 49747 变 54794 又变 54888）。
服务器上直接跑 CLI 把端口钉死：

```ini
# /etc/systemd/system/dsh.service
[Unit]
Description=DeepSeek Harness (dsh web)
After=network-online.target

[Service]
Type=simple
User=qqbot
WorkingDirectory=/home/qqbot
# ⚠️ 用 /usr/bin/env 而不是写死路径 —— 见第 4 章 203/EXEC 的坑
ExecStart=/usr/bin/env dsh web --host 127.0.0.1 --port 3080 --no-open
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

**装 preset 和 MCP**（桥接自带脚本）：

```bash
cd ~/qq-bridge && node scripts/setup-dsh.mjs
# 再做一次独立验证，别只听脚本说"成功"
node scripts/verify-agent-presets-017.mjs http://127.0.0.1:3080
# → ✅ agentPresets/list 含 qq-chat / qq-chat-v2，broken 为空
```

### 2.4 qq-bridge（中间人）

```bash
git clone https://github.com/Derpyu520/qq-bridge.git ~/qq-bridge
cd ~/qq-bridge && npm install
```

`config.json` 里几个必须改对的：

```json
{
  "dsh":      { "baseUrl": "http://127.0.0.1:3080" },        // 和 dsh.service 钉的端口一致
  "snowluma": { "homeDir": "/home/qqbot/aiQQ/deploy/snowluma/data" },  // 用来发现 OneBot token
  "allow":    { "groups": [], "private": ["你的QQ号"] }
}
```

**关键机制：桥接会自动从 `snowluma.homeDir/config/onebot_<uin>.json` 里发现 OneBot 的
HTTP/WS token**，所以不用手工抄 token。

> ⚠️ **这里有个坑：HTTP 和 WS 用的是两个不同的 accessToken。**
> 症状是 WS 反复 `rejected unauthorized WebSocket upgrade`，而 HTTP 是通的。
> 更麻烦的是 SDK 只发 `error` 事件、**从不发 `close`**，所以自带的"重连自愈"永远不触发。
> 修法：在 `bot.connect()` 前先调一次 token 发现，并给 `bot.on('error')` 也挂上自愈。

systemd 单元：

```ini
# /etc/systemd/system/qq-bridge.service
[Unit]
Description=qq-bridge (SnowLuma/QQ <-> DSH)
After=network-online.target docker.service
Wants=docker.service

[Service]
Type=simple
User=qqbot
WorkingDirectory=/home/qqbot/qq-bridge
ExecStart=/usr/bin/env node src/bridge.js
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

启用并验证：

```bash
sudo systemctl enable --now qq-bridge
sudo journalctl -u qq-bridge -n 30 --no-pager
# 期望看到：
#   已发现 SnowLuma：账号 <QQ号>（WS ws://...:3001）
#   SnowLuma 已连接
#   机器人昵称: xxx
#   DSH 已就绪（模式: reserved2）
```

### 2.5 数据搬迁（"程序在云上，灵魂还得搬过去"）

**要搬什么、不要搬什么** —— 这个判断很重要：

| 搬 | 为什么 |
| --- | --- |
| `~/.dsh/.credentials.yaml` | API 凭证，没它 AI 不会说话 |
| `~/.dsh/meme-packs/` | 表情包图库 |
| `qq-bridge/roles/*.md` | 人格卡 |
| `qq-bridge/config.json` | 改成服务器版 |
| `qq-bridge/state/*` | **记忆、会话映射、黑话、token 记账** |

| **不搬** | 为什么 |
| --- | --- |
| `~/.dsh/sessions/` | 里面是**机器相关**的路径和会话（`--home-qqbot-qq-bridge-state-agents--` 这种目录名是按绝对路径生成的，换机器就失效） |
| `~/.dsh/cache`、`attachments` | 缓存和临时附件 |
| `~/.dsh/profiles/*/node_modules` | 插件程序，服务器上重装 |

> ⚠️ **最容易漏的一个：人格不会自动跟过来。**
> `roles/*.md` 只是"有哪些人格"，**"当前启用哪个"记在 `state/current-role.json`**。
> 只传 `roles/` 的话，服务端 `/api/status` 里是 `"role": null`，
> AI 会按默认 coding agent 说话而不是你的人设。

## 第 3 章 上线后的运维

### 3.1 三个"体检"入口

| 看什么 | 命令 / 地址 |
| --- | --- |
| 服务活着吗 | `systemctl is-active dsh qq-bridge; docker ps` |
| 桥接自述状态 | `curl -H "x-console-token: $(cat state/console-token)" localhost:3100/api/status` |
| QQ 登录态 | `docker exec snowluma supervisorctl status` + `docker logs \| grep 'login detected'` |

`/api/status` 是诊断时最有用的一条，它一次给出：模式、人格、`dshReady`、
白名单、以及**最近的活动流水**（谁发了什么、AI 调了什么工具、成功几条）。

### 3.2 内存调优（2G 机器的必修课）

**症状**：机器还在 ping 得通、22 端口 TCP 能连上，但 **SSH 的 banner 永远不来**。

**先量化再动手**，`sar` 能看到历史：

```bash
sar -r -s 02:00:00 -e 02:30:00   # 内存
sar -q -s 02:00:00 -e 02:30:00   # 负载
```

当时的真实数据：

```
%memused 73~75%     ← 内存"没满"
%swpused  0.00%     ← swap 一次没用过
ldavg-1   22 → 32   ← 2 核机器，超载 16 倍
blocked   21        ← 21 个进程卡在不可中断 I/O 等待（D 状态）
```

**关键推理**：内存没满、swap 没用，负载却高到 32、21 个进程卡 D 状态 ——
这不是"内存不够"，而是**内核在做 direct reclaim（直接内存回收）**，
进程全被卡在分配内存那一步，连 sshd 都抢不到 CPU。

**顺着这条线找到真凶**：

```bash
grep -E '^(AnonPages|Slab|MemAvailable):' /proc/meminfo
# → AnonPages: 1072916 kB   1.05GB 全是「可换出的进程匿名页」
cat /proc/sys/vm/swappiness
# → 0    ← 元凶
```

`swappiness=0` 让内核**几乎不肯把冷页换出去**，宁可做 direct reclaim。
于是同样的 1.7GB 内存，明明可以靠换页撑住，却被自己卡死了。

**修法有两个层次**：

```bash
# ① 改 swappiness —— 但文件名必须排在阿里云那个之后！
#    阿里云镜像自带 /etc/sysctl.d/99-apsara-sysctl.conf 写死 vm.swappiness = 0
#    sysctl 按文件名字典序加载、后者覆盖前者，而 "99-aiqq" < "99-apsara"（第二位 i < p）
#    → 用 99-zz- 前缀
sudo tee /etc/sysctl.d/99-zz-aiqq-mem.conf >/dev/null <<'EOF'
vm.swappiness = 100
vm.vfs_cache_pressure = 50
EOF
sudo sysctl --system
cat /proc/sys/vm/swappiness      # 必须确认是 100，不是 0

# ② 加 zram（内存里的压缩块设备当 swap）
sudo apt-get install -y zram-tools
sudo tee /etc/default/zramswap >/dev/null <<'EOF'
ALGO=zstd
PERCENT=60
PRIORITY=100        # 必须高于磁盘 swapfile 的 -2，保证优先用 zram
EOF
sudo systemctl restart zramswap
swapon --show       # /dev/zram0 应排在 /swapfile 前面
```

效果对比（同一台机器）：

| 指标 | 调优前 | 调优后 |
| --- | --- | --- |
| MemAvailable | ~200 MB（冻结水位） | **~458 MB** |
| swap 使用 | 恒为 0（内核拒绝换页） | zram 活跃换页 |
| 负载 | 32 | < 1 |

**还有几条零成本的**：

```bash
# 关掉云主机上没用的：multipathd（21MB）、snapd（没装 snap 也白跑）
sudo systemctl disable --now multipathd.service multipathd.socket snapd.service snapd.socket
```

**不值得做的**（我一开始想错的方向）：
- **降分辨率**：800×600 的帧缓冲才 1MB 级，真正吃内存的是 Chromium 的多进程（625MB）
- **加磁盘 swap**：swappiness=0 的前提下加多少都白搭（实测 2GB swap 使用率恒为 0%）

### 3.3 QQ 侧的唯一故障模式：账号在别处登录

**这不是 bug，是 QQ 的设计**：同一账号在同一类设备上只能有一个登录。
容器里的 Linux QQ 算「电脑端」，你在另一台电脑登同一个号，就会把容器里这个顶掉。

症状：

```bash
docker exec snowluma supervisorctl status
# → qq RUNNING  但 uptime 只有几分钟（说明刚崩过重启）
docker logs snowluma | grep 'exited: qq'
# → WARN exited: qq (exit status 1; not expected)
docker logs snowluma | grep 'login detected'
# → 只有重启前的旧记录，重启后没有
```

**处理**：重新扫码（第 2.2 节）。**预防**：别在电脑上登这个号（手机一般没事）。

## 第 4 章 排错方法论（本文最有价值的部分）

### 4.1 分层定位：先确定是哪一层坏了

```
QQ 服务器 ──①── SnowLuma ──②── 桥接 ──③── DSH
```

**逐层体检命令**，一路往下走，第一个断掉的地方就是病灶：

| 层 | 怎么测 | 健康的表现 |
| --- | --- | --- |
| ① QQ 登录 | `docker logs snowluma \| grep 'login detected'` | 最近有 login detected |
| ② OneBot | `curl -X POST localhost:3000/get_login_info -d '{}' -H 'Authorization: Bearer <token>'` | `{"status":"ok",...}` |
| ② 桥接收 QQ | `journalctl -u qq-bridge \| tail` | `SnowLuma 已连接` |
| ③ DSH | `/api/status` 里的 `dshReady` | `true` |
| ③ AI 出话 | `/api/status` 里的 `activity` | 有 `工具统一发送：成功 N/N 条` |

**关键心法：不要看"服务还活着吗"，要看"数据流动到哪一步断的"。**
服务全是 `active` 却在装死，是这类系统最常见的故障形态。

### 4.2 三个真实案例的推理过程

#### 案例 A：机器人完全不回消息，但所有服务 active

**第一步：看桥接日志，找特征词**

```
19:04:21 [reserved2] 会话繁忙，暂存唤醒原因 private:xxx（poke@seq113）
19:06:18 [resolved2] 会话繁忙，暂存唤醒原因 private:xxx（private@seq116）
```

「会话繁忙」是关键线索 → 说明桥接认为 AI 正忙着，把新消息排队了。

**第二步：去读那段判定逻辑的源码**（不是猜）

```js
function isConversationBusyV2(key, st) {          // bridge.js:9480
  if (st && st.pendingWakeTimer) return true;
  if (pendingWakeKeys.has(key)) return true;
  const q = promptQueues.get(key);
  if (q && (q.running || q.queue.length > 0)) return true;
  const sid = state.sessions[key];
  if (sid && (v2TurnStartAt.has(sid) || collectors.has(sid))) return true;
  return false;
}
```

**四项全是内存状态** → 立刻明白**"重启 dsh"是错的解法**（重启只重新加载持久化数据，
这些内存标记不在里面）。这也解释了为什么重启后 1 分钟又报繁忙。

**第三步：去源码里找"官方解卡入口"**

```bash
grep -n "url.pathname === '/api/" src/bridge.js
```

找到 `/api/socialV2/wake`（它会先 `clearTimeout(st.pendingWakeTimer)`）
和 `/api/session/reset`（清掉全部四项 + 调 DSH 停掉在途任务）。

**心法：这个项目自带控制台 API，遇到问题先 `grep` 有没有现成的运维接口，
比自己想怎么绕强得多。**

#### 案例 B：整机假死，"服务看着都正常"

见 3.2 节。核心推理链是：

```
SSH banner 不来 + ping 通 + TCP 能连
  → 不是网络问题，是 sshd 抢不到 CPU
  → sar 看历史：内存没满、swap 没用、负载 32、21 个进程 D 状态
  → direct reclaim
  → /proc/meminfo 里 AnonPages 1.05GB（可换出）但 swappiness=0（不肯换）
  → 改 swappiness + 加 zram
```

**心法：`ss` 显示 TCP 建立但应用层无响应 = 进程调度/内存问题，不是网络问题。**

#### 案例 C：QQ 反复崩溃

```bash
docker logs snowluma | grep -c 'exited: qq'      # 崩了几次？1 次 = 偶发，持续 = 循环
docker exec snowluma supervisorctl status        # 看 uptime
```

只崩了一次 → 不是代码问题，找外部触发因素 → 用户想起"刚才登了那个账号"。

**心法：先分清"偶发"和"循环"。偶发就去问"刚才做了什么"，
循环才是要找的系统性问题。这一条帮我省了一小时。**

### 4.3 我自己犯的三个错（比成功的经验更值得学）

**错误一：加了个"卡死自动重启"看门狗，结果是帮倒忙。**

我按「10 分钟内 ≥2 次唤醒被暂存 且 成功发送 0 次 → 判定卡死」写了个每 5 分钟检查的看门狗。
**实测误判两次**，每次都在正常回合进行中把桥接重启、把对话打断。

为什么错？**这个判定条件与 AI 的「睡前观察」长等待完全重合**：
桥接规定每次沉睡前必须调 `qq_wait_for_messages(timeoutMs=300000~600000)`（最长 10 分钟），
而这 10 分钟里新消息**本来就**会被判繁忙而暂存、**本来就**不会有发送 —— 完美符合"卡死"特征。

**教训：写自动运维脚本之前，先问"正常情况会不会也长这样"。**
监控的误报比不监控更糟 —— 它会主动破坏正常流程。

**错误二：用了会丢数据的操作，而且没先备份。**

`/api/session/reset` 连 `recentMessages`（100 条）一起删了。删完新会话里的 AI 认为
"这段私聊没有历史"，于是只挂了个等待、**不回复积压的 30 条消息** —— 我把它修得更哑了。

**教训：任何"重置"类操作前先备份状态文件。** 这次运气好我备份了，
才能把记忆合并回去（会话映射在另一个文件里，所以恢复记忆不会把卡死的旧 session id 带回来）。

**错误三：测试时误杀了用户的程序。**

我做窗口清理测试时，匹配 `*WINDOW*` 去 kill，结果杀掉了用户的 WindowsTerminal，
连带桥接和 SnowLuma 全没了。

**教训：清理/测试脚本里，杀进程一定要用**精确匹配**（完整路径或 PID），
绝不用宽泛的通配。** 在用户的机器上操作时，这个原则更加重要。

## 第 5 章 踩坑总表（按根因分类）

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `docker pull` i/o timeout | 阿里云 ECS 上 Docker Hub 完全不通 | 配 registry-mirrors，**并实测拉 alpine 验证** |
| 2 | 装 docker-ce 速度 40KB/s | "官方源"在国内云主机上极慢 | 换发行版归档源（60MB/s） |
| 3 | `dsh.service` 崩溃循环 1/FAILURE | `credentials.yaml` 被 scp 传成 664 | `chmod 600` |
| 4 | `dsh plugin` 返回 127 | Linux 上 DSH 不自带 pnpm | `npm i -g pnpm` |
| 5 | `qq-bridge` 反复重启 203/EXEC | unit 写死 `/usr/bin/node`，实际在 `/usr/local/bin` | 用 `/usr/bin/env node` |
| 6 | 整机假死，SSH banner 不来 | 阿里云镜像把 `swappiness` 写死 0 → direct reclaim | `99-zz-` 前缀覆盖 + zram |
| 7 | 看起来"掉登录"，其实是静音 | 把 `SNOWLUMA_LOG_LEVEL` 调成 `warn`，`login detected` 是 INFO 级被吞了 | 诊断时保持 `info`，或直接用 `get_login_info` 问 |
| 8 | 人格没生效，`role: null` | 只传了 `roles/*.md`，没传 `state/current-role.json` | 补传状态文件 |
| 9 | WS 反复 `unauthorized` | OneBot 的 **HTTP 和 WS 用两个不同 token** | 连之前先做 token 发现 |
| 10 | QQ 崩溃后不自动登录 | 账号在别的电脑登录，把容器里的会话顶掉了 | 重新扫码；别在电脑上登这个号 |
| 11 | `docker exec` 里 `apt` 卡住 | 容器内网络/源与宿主不同 | 尽量在宿主操作，或用镜像自带工具 |

**一条元规律**：**11 个坑里，有 6 个是"我以为 A，实际是 B"造成的**（比如以为 127 是命令
找不到、以为服务 active 就是好的、以为日志级别不影响判断）。
**所以每一步都要有一个"独立验证"的动作** —— 比如配了加速器就真的拉一个镜像试试，
改了 swappiness 就真的 `cat` 一下确认是 100。

## 第 6 章 如果重来一次

### 6.1 顺序上会改的

1. **先做资源实测，再选规格。** 别按"估个大概"选 2G。跑起来后 `docker stats` +
   `ps -eo rss` 量一遍，再决定要不要升配。
2. **先在本地跑通整条链路**（本地能看到 QQ 窗口，排错成本低一个数量级），再迁云。
3. **一上来就把 systemd + 固定端口做好**。别先用 `nohup node src/bridge.js &` 凑合，
   后面会为了"它怎么断了"浪费大量时间。
4. **安全组只开 22，所有服务绑 127.0.0.1，用 SSH 隧道访问** —— 这个从一开始就做对了，
   是最省心的决定。

### 6.2 工具上会加的

- **一键启动/停止**（`云端一键启动.bat`）：检查服务 → 开隧道 → 带 token 打开控制台。
  日常用它，不用记一堆命令。
- **运维脚本放服务器上**（`/home/qqbot/unstick.sh` 之类），出问题时本地一行 ssh 就能跑。
- **所有"坑"当场写进 README**，并注明**根因**和**如何验证已修好**。
  这次写了第 9 节，回头看价值很高。

### 6.3 心态上最重要的一条

**这个项目每一层都有自己的"沉默失败"模式**：
QQ 崩了会自己重启、DSH 卡住不报错、桥接把消息默默排队、内核把自己卡死而不 OOM。
**表面"服务都 active"完全不能说明系统在工作。**

所以真正的能力不是"会敲这些命令"，而是：
**知道在每一层该看哪个指标，能区分"活着"和"在工作"。**

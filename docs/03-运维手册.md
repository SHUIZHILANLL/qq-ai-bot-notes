# 把整套 qq-bridge 部署到阿里云

适用：阿里云 **Ubuntu 22.04 / 24.04**（学生认证白嫖的 2核2G 或 2核4G 都行，2G 需要做内存优化）。

> ⚠️ **先读第三节「风控」**。技术上这套东西在云上跑得起来，但数据中心 IP + 异地登录是 QQ
> 风控的强信号。你已经被踢出过一个群（`result=110 你已被移出该群`），群友当时就在说
> 「要么被风控了」。搬上云之后这个信号更强。

---

## 一、架构

```
[阿里云 Ubuntu]
  ├─ Docker : SnowLuma          ← 官方镜像内置 Linux QQ + Xvfb + VNC + noVNC
  │            容器内 0.0.0.0，宿主机只映射到 127.0.0.1
  ├─ Node   : dsh web :3080     ← npm 全局装的 @deepseek-ai/dsh
  └─ Node   : qq-bridge         ← 连 127.0.0.1:3080 的 dsh

你家里的电脑 ──SSH 隧道──► 上面的 127.0.0.1 端口
```

**为什么三个必须都在这台机器上**，不能只搬 QQ 部分：

- 桥接的 DSH 鉴权是**从本机 `~/.dsh` 里的会话密钥离线铸 Cookie** 的 → 桥接和 DSH 必须同机。
- 把 DSH 留在家里、桥接放云上，就得把家里 PC 的 DSH 端口暴露到公网，而且 PC 一关就全死。

**一个意外的好处**：Windows 上 DSH 桌面版固定用 `dsh web --port 0`（**每次启动随机端口**，且不落
端口文件），桥接的 `baseUrl` 是启动时读死的 → DSH 一重启桥接就永久连不上（本机已经踩过这个坑）。
服务器上我们直接跑 CLI，能把端口**钉死在 3080**，从根上避开。

## 二、准备工作

### 服务器规格

| 项 | 建议 |
| --- | --- |
| 系统 | Ubuntu 22.04 或 24.04（文档和脚本都按这个写） |
| 配置 | **2核4G 最舒服**；2核2G 能跑但要做第五节的优化 |
| 磁盘 | 40G 起（Docker 镜像 + QQ 客户端 + 日志） |
| 带宽 | 1~3 Mbps 够用（QQ 文本流量很小） |

学生认证（飞天加速计划）常见是 2核2G 或 2核4G 二选一 —— **能选 4G 就选 4G**。

### ⚠️ 先建一个普通用户（别跳过）

**阿里云的 Ubuntu 镜像默认就是 `root` 登录**，而整套东西不该跑在 root 下
（systemd 服务以 root 运行等于把所有权限交出去）。`setup.sh` 会主动拒绝 root，所以先建用户：

```bash
# ① 用 root 登录服务器
ssh root@<服务器IP>

# ② 建普通用户（整套东西都用它跑）
adduser qqbot                 # 按提示设密码
usermod -aG sudo qqbot
mkdir -p /home/qqbot && chown qqbot:qqbot /home/qqbot

# ③ 切过去
su - qqbot
```

> 想以后直接 `ssh qqbot@<IP>` 登录，在服务器上执行
> `mkdir -p /home/qqbot/.ssh && cp /root/.ssh/authorized_keys /home/qqbot/.ssh/ 2>/dev/null; chown -R qqbot:qqbot /home/qqbot/.ssh`
> （如果你买的时候用的是密钥对而不是密码）。

### 把 deploy 目录传上去

在**你自己的电脑**上（PowerShell）：

```powershell
# 建目录并传（先以 root 传，再改属主，避免 qqbot 家目录权限问题）
ssh root@<服务器IP> "mkdir -p /home/qqbot/aiQQ"
scp -r C:\Users\UFO\Desktop\aiQQ\deploy root@<服务器IP>:/home/qqbot/aiQQ/
ssh root@<服务器IP> "chown -R qqbot:qqbot /home/qqbot/aiQQ"
```

> 首次连接会让你确认指纹，输 `yes`。
>
> **服务器版 `config.json` 已经替你生成好了**：`deploy/config.server.json`
> （`baseUrl` 钉 3080、`homeDir` 指向绑定挂载目录、清掉了失效的群）。第 7 步直接用它。

## 三、风控：动手前必须知道的事

搬上云会同时叠加三个风险信号：**数据中心 IP**、**异地登录**、**24 小时在线**。
QQ 对这类账号的常见处置是：临时冻结、强制下线、踢出群，严重时封号。

降低风险的实际做法，按性价比排序：

1. **别把主号放上去**。先用小号跑通全流程，观察一两周没问题再考虑换主号。
2. **不要频繁换 IP**。给 ECS 绑一个固定公网 IP（弹性公网 IP），别每次重启换一个。
3. **发消息节奏保守一点**。`config.json` 里 `socialV2.send.maxSendPerMinute`（默认 8）和
   `maxSendPerHour`（默认 60）可以再调小；`autoReplyCheckMs` 调大。
4. **别进大群**。你账号现在在一个 352 人的群里，群里人越多、越容易被举报。
5. **接受一个事实**：这套东西本质是在用协议端挂 QQ，腾讯一直在打击。风险无法归零。

## 四、部署步骤

### 1. 服务器准备（Docker + Node + dsh + systemd）

```bash
cd ~/aiQQ/deploy
bash setup.sh
```

脚本做这些事：装 Docker（走阿里云镜像源）、装 Node 24（走 npmmirror，国内直连 nodejs.org 常超时）、
`npm i -g @deepseek-ai/dsh`、建 SnowLuma 挂载目录、生成 `.env`（随机 VNC 密码 + 你的 uid/gid）、
装 systemd unit。**幂等，可以重复跑。**

⚠️ 最后如果不提示，记得**重新登录一次**（或 `newgrp docker`）让 docker 组生效。

**把 setup.sh 打印出来的 VNC 密码存好**，或者随时再看：

```bash
grep VNC_PASSWD ~/aiQQ/deploy/.env
```

### 2. 起 SnowLuma 容器

```bash
cd ~/aiQQ/deploy
docker compose up -d
docker compose logs -f --tail=50
```

首次启动日志里会有 WebUI 一次性管理员密码，记下来：

```bash
docker logs snowluma 2>&1 | grep -E "临时密码|initial credentials" | tail -1
```

确认容器健康：

```bash
docker exec snowluma getcap /usr/local/bin/node    # 期望含 cap_sys_ptrace=ep
docker exec snowluma supervisorctl status           # qq / snowluma 应为 RUNNING
```

### 3. 建 SSH 隧道，扫码登录 QQ

**在你自己的电脑上**开一个终端（PowerShell 或 Git Bash 都行），保持它开着：

```bash
ssh -N \
  -L 6081:127.0.0.1:6081 \
  -L 5099:127.0.0.1:5099 \
  -L 3000:127.0.0.1:3000 \
  -L 3001:127.0.0.1:3001 \
  -L 3080:127.0.0.1:3080 \
  -L 3100:127.0.0.1:3100 \
  qqbot@<服务器IP>
```

然后在本地浏览器打开 **<http://127.0.0.1:6081>** —— 这是 noVNC，你能看到容器里那个虚拟桌面上的
QQ 登录窗口，用**手机 QQ 扫码**登录。

> 登录态存在绑定挂载的 `~/aiQQ/deploy/snowluma/local` 里，之后重启容器不用重扫。

登录成功后，`hookAutoLoad` 会让 SnowLuma 自动从被动观察切到工作模式，不用去 WebUI 手动 Load。

### 4. 克隆桥接 + 打补丁

```bash
git clone https://github.com/Derpyu520/qq-bridge.git ~/qq-bridge
cd ~/qq-bridge
npm install
bash ~/aiQQ/deploy/patch-bridge.sh ~/qq-bridge
```

`patch-bridge.sh` 打的是两处**上游 v0.1.7 的真实 bug**（都已在本地验证过）：

- **SnowLuma token 自愈不触发**：HTTP token 与 WS token 是两个不同的值，而 SDK 构造只能给一个；
  用错 token 时握手被拒，SDK **只 emit `error`、从不 emit `close`**，而自愈只挂在 `close` 上 →
  永远不触发，桥接卡在「一次都连不上」。
- **角色卡「回复示例」误报**：判断用了 `\s+`，而 `\s` 会吃掉换行 → 对几乎任何多行中文人格卡误报。

脚本幂等（跑第二遍会跳过），打完会跑 `node --check` 风格的自检。**不打补丁，云上会重现同样的故障。**

### 5. 装 DSH 端（preset + MCP）

```bash
cd ~/qq-bridge
node scripts/setup-dsh.mjs
```

这一步会往 `~/.dsh/profiles/web/` 装 `qq-chat` / `qq-chat-v2` 两个 preset 和三个 MCP server。
**不需要重启 DSH**（该 profile 的 `patchReload: live` 会即时生效）—— 本机实测过，
`verify-agent-presets-017.mjs` 全绿。

验证：

```bash
node scripts/verify-agent-presets-017.mjs http://127.0.0.1:3080
```

### 5b. 装回你原来的 DSH 插件

服务器是全新的 `~/.dsh`，你在 Windows 上装过的插件不会跟过来（插件的**数据**在第 6 步拷，
**程序**要重装）。

`dsh plugin` 其实是 **pnpm 的直通包装**（`dsh plugin --profile web --help` 打出来的是 pnpm 的完整命令表），
所以加包用 `add`：

```bash
dsh plugin --profile web add dsh-meme dsh-whale-widget dshmarket
sudo systemctl restart dsh      # 装完重启 dsh 生效
```

你 Windows 上的 profile 现在装的是这几个（`^0.1.43` / `0.3.16` / `^1.66.2`），
另外两个 `qq-mode-console` / `qq-agent-presets` 是 `link:` 本地依赖，由第 5 步的
`setup-dsh.mjs` 自动接进去，**不要**用 `add` 装。

> 想确认版本，在 Windows 上跑 `dsh plugin --profile web list`。

### 6. 数据搬迁

把家里电脑这几样拷到服务器（`scp` 从你的电脑执行）：

| 从（你的 Windows） | 到（服务器） | 为什么 |
| --- | --- | --- |
| `C:\Users\UFO\.dsh\.credentials.yaml` | `~/.dsh/.credentials.yaml` | **DeepSeek API 凭证，没这个 AI 不会说话** |
| `C:\Users\UFO\Desktop\aiQQ\qq-bridge\config.json` | `~/qq-bridge/config.json` | 白名单、模型、各种调过的参数 |
| `C:\Users\UFO\Desktop\aiQQ\qq-bridge\roles\` | `~/qq-bridge/roles/` | 人格卡（含你那份 `闽越王-副本.md`） |
| `C:\Users\UFO\Desktop\aiQQ\qq-bridge\state\console-token` | `~/qq-bridge/state/console-token` | 控制台令牌（不拷也行，会重新生成） |
| `C:\Users\UFO\.dsh\meme-packs\` | `~/.dsh/meme-packs/` | 表情包图库 |
| `C:\Users\UFO\.dsh\dsh-expression.json` 等 | `~/.dsh/` | 表情/角色的插件数据 |

```powershell
# 在 Windows 上执行（用户名/路径按实际改）
scp C:\Users\UFO\.dsh\.credentials.yaml qqbot@<IP>:~/.dsh/
scp C:\Users\UFO\Desktop\aiQQ\qq-bridge\config.json qqbot@<IP>:~/qq-bridge/
scp -r C:\Users\UFO\Desktop\aiQQ\qq-bridge\roles qqbot@<IP>:~/qq-bridge/
scp -r C:\Users\UFO\.dsh\meme-packs qqbot@<IP>:~/.dsh/
```

**⚠️ 不要拷 `node_modules` 和 `state/sessions.json`**（前者平台相关，后者是机器相关的会话映射）。

**别忘了清掉 `config.json` 里的 `snowluma.accessToken`** —— 服务器上是全新的 SnowLuma 数据目录，
token 会重新生成。留空即可，桥接的自动发现会处理（前提是第 7 步的 `homeDir` 配对）。

### 7. 改 `config.json` 的三处

```bash
nano ~/qq-bridge/config.json
```

```jsonc
{
  "dsh": {
    "baseUrl": "http://127.0.0.1:3080",   // ← 服务器上端口是钉死的
    // ...
  },
  "snowluma": {
    "wsUrl": "ws://127.0.0.1:3001",
    "httpUrl": "http://127.0.0.1:3000",
    "accessToken": "",                     // ← 清空，让它自动发现
    "launcherPath": "",
    "homeDir": "/home/qqbot/aiQQ/deploy/snowluma/data"   // ← ★ 关键
  },
  "allow": {
    "private": [<QQ号>],
    "groups": [891351899]                  // ← 把已被踢出的 692905367 删掉
  }
}
```

> **`homeDir` 为什么是关键**：桥接会扫 `<homeDir>/config/onebot_<uin>.json` 来自动发现
> HTTP/WS 两个 token。Docker 用命名卷的话这些文件在宿主机上读不到；本套用**绑定挂载**
> 就是为了让 discovery 继续生效。

### 8. 启动并验证

```bash
# DSH（需要先有 ~/.dsh/.credentials.yaml）
sudo systemctl enable --now dsh
journalctl -u dsh -f          # 看到监听了 3080 就 Ctrl+C

# 桥接
sudo systemctl enable --now qq-bridge
journalctl -u qq-bridge -f
```

期望看到：

```
已发现 SnowLuma：账号 <QQ号>（WS ws://127.0.0.1:3001）
SnowLuma 已连接：ws://127.0.0.1:3001
机器人昵称: xxx
DSH 已就绪（模式: reserved2）
```

再跑一遍桥接自带的自测（会建一个独立测试会话，不影响现有会话）：

```bash
cd ~/qq-bridge && node src/self-test.js http://127.0.0.1:3080
```

> 注意：`self-test.js` 把 `3080` 写死在默认参数里、**不读 config.json**，所以必须显式传地址。

## 五、2核2G 的内存优化

实测这套大约占 1.0~1.8GB，2G 的机器会很紧。按性价比排序：

1. **加 2G swap**（`setup.sh` 会问你要不要建）。慢，但能防 OOM 杀进程。
2. **调小虚拟屏幕**：`.env` 里 `SNOWLUMA_SCREEN=1280x720x16`（默认 1920x1080x24）。
   二维码窗口不需要 1080p，省内存也省 CPU。
3. **关掉用不上的 QQ 功能**：`SNOWLUMA_QQ_FLAGS` 里默认已经关了 GPU，
   可以再加 `--js-flags=--max-old-space-size=256`。
4. **限制 DSH 的并发**：别同时开很多会话。
5. **看谁在吃内存**：
   ```bash
   docker stats --no-stream
   ps -eo pid,rss,comm --sort=-rss | head -15
   free -h
   ```

如果 OOM 频繁（`dmesg | grep -i oom`），说明 2G 真的不够，考虑升级到 4G。

## 六、安全组与端口：**这一节别跳过**

SnowLuma 官方文档对这几个端口是**红字警告**的：`6081`(noVNC) / `5099`(WebUI) / `3000` / `3001`
**能完全控制你的 QQ**。本套的 `docker-compose.yml` 已经把它们全部绑到宿主机 `127.0.0.1`，
**外网根本连不上** —— 这是有意的，别改。

所以阿里云**安全组只需要放行 SSH**：

| 端口 | 放行 | 说明 |
| --- | --- | --- |
| 22 | ✅ 必须 | 建议限制来源 IP 为你自己的出口 IP |
| 80 / 443 | ❌ | 不需要（而且阿里云未备案会拦） |
| 6081 / 5099 / 3000 / 3001 / 3080 / 3100 | ❌ **绝对不要** | 全靠 SSH 隧道 |

需要访问时开第 3 步那个 SSH 隧道即可。隧道关掉，这些端口对外就等于不存在。

> **VNC 密码一定要强**。虽然绑在 127.0.0.1，但万一你把隧道开给了别人、
> 或者哪天改错了 compose 文件，弱密码就等于 QQ 裸奔。

## 八、排障

| 症状 | 先查什么 |
| --- | --- |
| 桥接日志刷 `SnowLuma 错误: {}` | 看 `docker logs snowluma` 有没有 `rejected unauthorized WebSocket upgrade`。有 → token 不对，检查 `homeDir` 是否指对、`accessToken` 是否被旧的占住 |
| `SnowLuma 已连接` 但 QQ 上没反应 | `allow.groups` / `allow.private` 白名单；以及 QQ 是不是根本没消息进来 |
| 连不上 DSH | `journalctl -u dsh`，确认监听 3080；`~/.dsh/.credentials.yaml` 在不在 |
| Wolf/风控掉线 | 看 SnowLuma 日志有没有 `session closed`；QQ 客户端可能被强制下线，去 noVNC 里看 |
| 容器起不来 | `docker compose logs`；重点看 `shm_size: 1gb` 和 `SYS_PTRACE` 那两行有没有被删 |
| 注入失败 | `docker exec snowluma getcap /usr/local/bin/node` 要含 `cap_sys_ptrace=ep`；`cat /proc/sys/kernel/yama/ptrace_scope` 不能是 3 |
| 内存被打满 | 见第五节。`dmesg \| grep -i oom` |

## 九、实战踩坑记录（2026-09-29 真实部署，全部已修进脚本）

这一节是**实际部署时踩到的**，不是推测。都已修进 `setup.sh` / systemd 模板，重装不会再遇到。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `docker pull` 报 `dial tcp ... i/o timeout`；`registry-1.docker.io` HTTP 000 | 阿里云 ECS 上 **Docker Hub 完全不通** | `setup.sh` 自动写 `/etc/docker/daemon.json` 配 4 个加速器，并**实测拉 alpine 验证** |
| 2 | 装 docker-ce 二十多分钟只下了 50MB（≈40 KB/s） | **Docker 官方源在 ECS 上极慢**；而 Ubuntu 归档源实测 **60 MB/s**（88MB 一秒下完） | 改用 `apt-get install docker.io docker-compose-v2`（Ubuntu 24.04 里就是 **Docker 29.1.3 + compose 2.40.3**，功能完全够） |
| 3 | `dsh.service` 崩溃循环，`status=1/FAILURE` | DSH 安全护栏：`~/.dsh/.credentials.yaml` 被 scp 传成 **mode 664**，它要求 600，直接拒绝启动 | `chmod 600 ~/.dsh/.credentials.yaml` |
| 4 | `dsh plugin` 返回 **127**；插件装不上 | **Linux 上 DSH 不自带 pnpm**（Windows 桌面版自带），`dsh plugin` 是 pnpm 直通包装 | `sudo npm i -g pnpm` |
| 5 | `qq-bridge.service` 反复重启，`status=203/EXEC` | unit 模板写死了 `ExecStart=/usr/bin/node`，但 Node 是 npmmirror 二进制包装到 **`/usr/local/bin/node`** | 改用 `ExecStart=/usr/bin/env node`（走 PATH，不写死绝对路径） |
| 6 | **整机假死**：ping 通、22 端口 TCP 能连上，但 SSH banner 永远不来 | **阿里云镜像自带 `/etc/sysctl.d/99-apsara-sysctl.conf` 把 `vm.swappiness` 写死为 0**。内核于是几乎不肯换出冷页，转去做 **direct reclaim** → 21 个进程卡 D 状态、负载飙到 32（2 核机器）、sshd 抢不到 CPU 回应握手。`sar` 显示当时 `%memused` 只有 73~75%、**swap 使用率 0%** —— 内存没「满」，但内核把自己卡死了 | 见下方「swappiness 这条最隐蔽」 |
| 7 | 已登录的 QQ 看起来「掉登录」了 | 其实是把 `SNOWLUMA_LOG_LEVEL` 调成 `warn`，**把 `login detected` 这条 INFO 日志静音了**，误判成掉登录 | 诊断时用 `get_login_info` 直接问，别只看日志 |

### swappiness 这条最隐蔽，单独说

修法**不是**简单写个 sysctl 文件就行 —— **文件名必须排在阿里云那个之后**：

```bash
# ❌ 错：sysctl 按文件名字典序加载、后者覆盖前者，而 "99-aiqq" < "99-apsara"（第二位 i < p）
/etc/sysctl.d/99-aiqq-mem.conf          # 被覆盖，swappiness 仍是 0
# ✅ 对：用 99-zz- 前缀确保排在最后
/etc/sysctl.d/99-zz-aiqq-mem.conf
```

再配合 **zram**（内存里的压缩块设备当 swap，优先级高于磁盘 swapfile）：

```bash
sudo apt-get install -y zram-tools
# /etc/default/zramswap → ALGO=zstd / PERCENT=60 / PRIORITY=100
sudo systemctl restart zramswap
```

这样同样的 1.7GB 等效可用内存明显变大（文本类数据压缩比一般 2~3 倍），
而且内核愿意主动换页，不会再走到 direct reclaim 那一步。

脚本：[`tune-swap-zram.sh`](tune-swap-zram.sh)。**验证是否生效**：

```bash
cat /proc/sys/vm/swappiness     # 应为 100，不是 0
swapon --show                   # /dev/zram0 应排在 /swapfile 前面
```

### 内存看门狗（踩过假死之后加的）

`mem-watch/` 里是个 systemd timer，每分钟检查 `MemAvailable`，分级降压：

| 条件 | 动作 | 影响 |
| --- | --- | --- |
| < 200MB 连续 3 分钟 | 重启 `dsh` + `qq-bridge` | **不动 QQ 登录态** |
| < 120MB 连续 4 分钟 | 重启 `snowluma` 容器 | QQ 可能要重新扫码 |
| < 70MB 立即 | 停掉 `qq-bridge` | 保住机器可用，防止 SSH 失联 |

> ⚠️ 阈值必须**高于**实测的冻结水位。第一版写成 150MB 是错的 —— 实测冻结那一刻是
> **200MB 可用**，150MB 根本不会触发。装看门狗前一定要先量出自己机器冻结时的水位。
>
> 日志：`/var/log/aiqq-mem-watch.log`

### dsh 内存 GC（`aiqq-dsh-gc.timer`）与它的阈值陷阱

每 5 分钟看一次 `dsh.service` 的 `MemoryCurrent`，超阈值就重启 `dsh` + `qq-bridge`
（**不动 snowluma 容器，QQ 登录态不受影响**）。

> ⚠️ **阈值必须明显高于 dsh 的「正常水位」，否则它会把正常回合打断、把系统弄坏。**
>
> 第一版我定的阈值是 **400MB**，而实测 dsh 带着一段长对话的**正常水位就是 400~460MB**
> （那一刻整机才用 1087/1740MB、可用 653MB，**根本没有内存压力**）。
> 结果它每十几分钟就在**回合进行中**重启一次 dsh —— 而"回合进行中重启 dsh"正是把桥接
> 留在「会话繁忙」状态的原因。**看门狗把自己变成了故障源**（2026-10-08 实测：
> 07:36 重启 → 07:42 还正常 → 07:47 又重启 → 之后机器人哑了一上午）。
>
> 现在的配置：**阈值 800MB + 需连续 3 次（15 分钟）超阈值才动手**。
> 调阈值：`sudo systemctl edit aiqq-dsh-gc.service` 加 `Environment=DSH_MEM_THRESHOLD_MB=xxx`。
> 判断当前水位是否正常：`systemctl show -p MemoryCurrent --value dsh.service | awk '{printf "%d MB\n",$1/1048576}'`
>
> 日志：`/var/log/aiqq-dsh-gc.log`（里面出现 `重启` 就说明又触发了，要看是不是误报）

### 「机器人突然不回消息」的排查与解卡（2026-09-30 实测，含一次自己造的坑）

**症状**：QQ 上发消息完全没反应，但服务全是 `active`、容器正常、`dshReady: true`。

**一看就知道的日志特征**（`journalctl -u qq-bridge`）：

```
19:04:21 [reserved2] 会话繁忙，暂存唤醒原因 private:xxx（poke@seq113）
19:06:18 [reserved2] 会话繁忙，暂存唤醒原因 private:xxx（private@seq116）
19:08:18 [reserved2] 会话繁忙，暂存唤醒原因 private:xxx（private@seq117）
```

同时 `/api/status` 的 `activity` 里，最后一条 `工具统一发送：成功` 停在很久以前。

**「繁忙」的判定在桥接这边**（`bridge.js:9480` `isConversationBusyV2`），四项**全是内存状态**：

```js
if (st && st.pendingWakeTimer) return true;
if (pendingWakeKeys.has(key)) return true;
const q = promptQueues.get(key);
if (q && (q.running || q.queue.length > 0)) return true;
const sid = state.sessions[key];
if (sid && (v2TurnStartAt.has(sid) || collectors.has(sid))) return true;
```

**解卡工具是控制台的两个接口，不要靠重启 dsh** —— 重启只重新加载持久化状态，卡住的
内存标记不会清掉（实测重启 dsh + 桥接后 1 分钟又报繁忙）。按代价从小到大：

| 顺序 | 接口 | 清掉什么 | 代价 |
| --- | --- | --- | --- |
| 1️⃣ 先试 | `POST /api/socialV2/wake` `{"key":"private:xxx","reason":"admin"}` | `st.pendingWakeTimer`（4607-4611 行会先清它再唤醒） | **无**，不丢记忆 |
| 2️⃣ 再试 | `POST /api/session/reset` `{"key":"private:xxx"}` | `pendingWakeKeys`(6498) + `collectors`/`v2TurnStartAt`(6471-6474) + 队列(6485) + 定时器(6496)，并 `api.stopSessionWork()` 停掉 DSH 侧在途任务 | **会清空该会话上下文**（`socialV2.conversations.delete`） |

> 用 `POST /api/session/reset` 之前**务必先备份** `state/social-v2.json` ——
> 它连 `recentMessages`(默认 100 条) 一起删。删掉后新会话里的 AI 会认为
> 「这段私聊没有历史、没有新消息可读」，于是**只挂一个等待、不回复积压消息**（实测踩到）。
> 备份后可以把 `conversations[key]` 单独合并回去（会话映射在 `sessions.json` 里，
> 所以恢复它**不会**把卡死的旧 session id 带回来）。

#### ⚠️ 不要加「卡死自动重启」看门狗 —— 我自己加了，结果是帮倒忙

我按「10 分钟内 ≥2 次唤醒被暂存 且 成功发送 0 次 → 判定卡死」写了个看门狗（每 5 分钟一次），
**实测两次误判**（19:11:07、19:21:43），每次都在正常回合进行中重启桥接把它打断。

原因：**这个条件与 AI 的「睡前观察」长等待完全重合。** 桥接规定每次沉睡前必须调用
`qq_wait_for_messages(timeoutMs=300000~600000)`（最长 10 分钟，见 `bridge.js:9307`），
而这 10 分钟里新消息**本来就**会被判繁忙而暂存、**本来就**不会有发送 —— 完美符合"卡死"特征。
于是看门狗每 10 分钟打断一次，AI 永远没机会回复。

顺带记录踩过的两个小坑：

- **冷却期**：卡死判定回看窗口内的日志里还留着重启**之前**的「暂存唤醒」记录，重启后第一次
  检查会立刻又判定卡死 → 重启死循环。要加判定就必须先用
  `ActiveEnterTimestampMonotonic` 算服务已运行时长，不足一个窗口就跳过。
- **`qq_wait_for_messages` 本身没有死锁**：它轮询 `st.lastUnreadSeq`（`bridge.js:5623/5636`），
  新消息一定会让它返回。所以「等待时消息进不来」是**假象** —— 消息进了未读、只是这个回合
  还没结束。同一会话同时只允许一个等待（5585 行，重复调用返回 429）。

### 内存都花在哪了（实测，2核2G 机器）

| 组件 | 占用 | 说明 |
| --- | --- | --- |
| **snowluma 容器** | **~750 MB** | 其中 QQ 的 Chromium 多进程约 625MB（154+144+94+76+59+51+26 MB），snowluma node 97MB，Xvfb 23MB，supervisord 21MB |
| dsh.service | ~295 MB | 会随对话时长增长（实测聊 5 小时后把机器顶穿） |
| qq-bridge.service | ~88 MB | |
| docker + containerd | ~99 MB | |
| 系统 + journald | ~120 MB | multipathd 21MB、snapd 可关 |
| **合计** | **~1.35 GB / 1.74 GB** | |

**结论：容器那 750MB 是结构性的**（Linux QQ 就是 Chromium），改参数只能小修小补。
真正的杠杆是 swappiness + zram（让同样的内存装下更多），以及控制 DSH 的累积增长。

### 其余减内存措施（按性价比排，实测）

| 措施 | 效果 | 说明 |
| --- | --- | --- |
| **`vm.swappiness` 0→100 + zram** | **量级最大** | 见上文。核心不是"省"，而是让内核肯换页、且换页发生在内存里 |
| **dsh 内存回收定时器** | 200~300 MB | `trim-memory.sh` 装的 `aiqq-dsh-gc.timer`，每 15 分钟检查，RSS > 400MB 就重启 dsh + qq-bridge（**不动 QQ 登录态**）。阈值用 `systemctl edit aiqq-dsh-gc.service` 改 |
| **卸掉 `dshmarket` + `dsh-whale-widget`** | 20~50 MB | 桌面插件市场 / 挂件，无头服务器上纯占内存。⚠️ 必须**同时**从 `package.json` 的 `dependencies` 和 `dsh.profile.bundles` 里删 —— 只删前者会让 DSH 报「无法解析 bundle」起不来 |
| 关 `multipathd` / `snapd` | 40~60 MB | 云主机上都没用 |
| 不用扫码时停 VNC 栈 | **仅 32 MB** | Xvfb 23 + x11vnc 6 + fluxbox 3。**不值得折腾**（原先估 60~80MB，实测差一倍多） |
| 给 QQ 的 V8 堆设上限 | 50~100 MB | **有风险**。用 512MB；`--max-old-space-size=224` 实测会把 QQ 搞得连登录都不响应 |

**没用的做法**（别浪费时间）：

- **降分辨率**：800×600 的帧缓冲才 1MB 级，真正吃内存的是 Chromium 的多进程，省不出东西
- **加磁盘 swap**：在 swappiness=0 的前提下加多少都白搭（实测 2GB swap 使用率恒为 0%）。先修 swappiness，swap 才有意义

**调优后实测对比**（同一台 2核2G）：

| 指标 | 调优前 | 调优后 |
| --- | --- | --- |
| MemAvailable | ~200 MB（冻结水位） | **~458 MB** |
| dsh RSS | ~337 MB | **270 MB** |
| swap 使用 | 恒为 0（内核拒绝换页） | zram 活跃换页（23 MB 压缩后） |
| 负载 | 32（2 核机器） | < 1 |

### 两个容易漏的非脚本项

- **人格不会跟过来**。`roles/*.md` 是内容，但「当前启用哪个人格」记在 `qq-bridge/state/current-role.json`。
  只传 `roles/` 的话服务端 `"role": null`，AI 会按默认 coding agent 说话。**要把这个文件也传过去**
  （或部署后在控制台「人格与角色」里点一下）。
- **scp 会改变文件权限**。凡是 DSH 读的敏感文件（`.credentials.yaml`），传完都要 `chmod 600`。

### 一个和端口有关的历史坑

DSH 桌面版固定用 `dsh web --port 0`（随机端口，且在 Windows 上不落端口文件），而桥接的
`dsh.baseUrl` 是启动时读进内存的 —— **DSH 一重启桥接就连不上**（本机反复踩过，端口从 49747
变成 54794 又变成 54888）。服务器上直接跑 CLI，把端口钉死在 **3080**，从根上避开。
